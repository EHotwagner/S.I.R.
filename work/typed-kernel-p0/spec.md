# Typed Kernel P0 Specification

Prose status: specified

## User Value
A rule-kernel author can distinguish reusable specification substrate from S.I.R.-owned gameplay semantics using checked, content-addressed examples.

## Scope
- SB-001: Capture and verify the P0 S.I.R. corpus baseline, authoring-cost evidence, candidate shared concepts, and explicit domain ownership without changing authoritative behavior.

## Non-Goals
- SB-002: Do not implement the P1 AST/EDSL, migrate a rule, extract a package,
  introduce coordination mutations, or change any authoritative rule behavior.
- SB-003: Do not promote test-only predicate or supersession examples into the live registry.
- SB-004: Do not infer missing historical authoring-session measurements.

## User Stories
- US-001 (P1): As a kernel designer, I can inspect a reproducible baseline and decide
  which concepts have enough checked uses to enter the P1 pilot.
- US-002 (P1): As a S.I.R. maintainer, I can prove the baseline adds no gameplay
  authority and detect stale, incomplete, or non-portable pilot evidence.

## Acceptance Scenarios
- AC-001 [US-001] [FR-001] [FR-003]: Given the current corpus and lifecycle receipts,
  when the P0 capture runs, then a canonical manifest and report name every selected
  surface, its authority class, its artifact digest, the evidence available, and any
  honestly unknown measurement.
- AC-002 [US-002] [FR-002] [FR-004]: Given a clean checkout, when the P0 check runs
  under .NET and Fable, then generated bytes match the committed baseline and all
  existing authoritative corpus fixtures remain byte-identical.
- AC-003 [US-002] [FR-002] [FR-004]: Given a changed digest, omitted required surface,
  or divergent cross-runtime baseline, when the check runs, then it fails with the
  changed obligation named.
- AC-004 [US-001] [FR-003] [FR-005]: Given a proposed reusable concept, when the
  report is reviewed, then it names at least two checked uses or rejects the concept,
  while gameplay values and interpreters remain explicitly S.I.R.-owned.

## Functional Requirements
- FR-001: A committed machine-readable manifest selects representative fact, formula, transition, algorithm, evidence, generated-projection, replay, predicate-fixture, and supersession-fixture surfaces and binds every artifact to SHA-256. (Stories: US-001; Acceptance: AC-001)
- FR-002: One repository command regenerates the manifest deterministically, rejects drift, and proves the existing native/Fable corpus parity path remains green. (Stories: US-001; Acceptance: AC-001)
- FR-003: A P0 report records authoring cost, semantic-diff quality, diagnostics, elapsed evidence, reusable candidates with at least two checked uses, and S.I.R.-owned non-transferable concepts. (Stories: US-001; Acceptance: AC-001)
- FR-004: The baseline MUST preserve existing manifest, coverage, representative application, coherence, and .NET/Fable conformance bytes; it MUST add no production dependency and perform no network or mutable external I/O. (covers AC-002, AC-003)
- FR-005: Each candidate shared concept MUST cite at least two checked uses across rule, lifecycle, replay, projection, evidence, or future coordination examples; hypothetical candidates MUST be excluded. (covers AC-004)
