- **Kind:** capability-gap
- **Impact:** Every instance shipped through green gates, and one passed a fully green hosted CI run. Six of the seven were invisible to my own adversarial self-testing. The recurrence is the finding: one instance is a mistake; seven in one item, across three independent passes each finding escapes the previous ones missed, is a property of how these gates are built and checked.
- **Expected:** A gate ships with evidence it can fail, and its assertion is capable of failing for every case its message claims to cover.
- **Observed:** Seven instances, one shape — a confident general claim resting on a narrow predicate. Grouped by the pass that found them.

  *A — the registry-relative assertion.* Deleting `feedback-audit` from `subjectOrder` shrank the sweep silently, because every sweep assertion was written *relative to* `subjectOrder` (`subjectOrder.every(...)`, `swept.subjects.length === subjectOrder.length`).   *B — the token blocklist.* `assert.doesNotMatch(sweepJob, /\|\s*head\b/u, "no early-closing pipe in a pipefail step")` banned one token while its message declared a general property. `awk 'NR==1{print; exit}'`, `grep -m1 ''` and `sed -n '1{p;q}'` all pass it and all SIGPIPE their producer under `-o pipefail` — intermittently, at 5/10, 3/10 and 1/10. Killed by executing each pipeline's consumer under GitHub's exact bash invocation against a producer large enough that an early exit always has pending writes — measured 0/20 failures for `sed -n '1p'` and `cat`, 20/20 for all four early-exit forms.

Killed by absolute per-subject selection pins plus plan and subject shape pins.

D and E: presence assertions cannot see an *addition* — `continue-on-error` and `if: false` add something beside what is checked rather than removing it, so every "is it wired?" assertion stays true while the job is neutralised. F is a different and simpler cause: deleting the `push` leg is precisely what a presence assertion catches, and it survived only because **no assertion for that leg existed at all**. Bundling the two under one lesson would be the more quotable claim and the wrong one. B and G: **both my gates and the repository's existing ones check workflow *structure* as text and never *execute* it** — `test-workflow-action-contract.mjs` and `test-ci-route.mjs` parse `ci.yml` for pins, headers, timeouts, `needs` edges and `if:` expressions, and neither runs a single `run:` block.

#### §4.5 The documented double-quoted invocation style silently corrupts free-text arguments across every coordination command

- **Kind:** defect
- **Impact:** A silent corruption path in the documented invocation style of **every** `fsgg-coord` and `feedback-tool` command that takes prose. It has already corrupted one committed feedback checkpoint and one inter-lane coordination message in this single cycle. There is no signal at the call site: the command succeeds, exits 0, and the corrupted text is what persists.
- **Expected:** Recorded or transmitted text matches what the author wrote, or the command refuses.
- **Observed:** Both skills document these commands only as bash invocations with **double-quoted** free-text arguments. Any backtick pair in that text is command-substituted by the shell before the binary ever sees it. Evidence text and coordination messages routinely contain backticked identifiers and code, so this is the normal case, not an edge case. Two first-hand instances:

  *Instance 1 — a committed checkpoint.* A backtick pair in `--evidence` was substituted; bash emitted `invalidated: command not found` to stderr, the tool then printed `appended checkpoint` and exited 0, and the stored JSONL read `where  holds only citations` with the identifier deleted. `validate-checkpoint-state` subsequently reported **PASS** on the corrupted content. Repaired by rewriting the JSONL line — which means that specific PASS is no longer re-verifiable, since the record it passed on no longer exists; what remains re-verifiable is the repaired line's manual provenance, visible as an unescaped `+00:00` where tool-written lines carry `\u002B00:00`.

  *Instance 2 — a coordination message, and the sharper one.* A backticked CLI name inside a double-quoted `fsgg-coord say` argument caused bash to **actually execute `/usr/bin/who`**. The engine printed `who: unrecognized option '--json'` to stderr, printed `said to rook-e7e8 on S.I.R.#255` to stdout, and **exited 0**. The send succeeded while silently transmitting text with the identifier deleted, to a lane that was using my messages to author a contract document.

  The failure mode is what makes it serious: success on stdout, a zero exit code, and a diagnostic on stderr that reads as though it came from an unrelated program. Nothing at the call site indicates that anything went wrong. I caught the second instance only because I happened to read a stray diagnostic, and the first only because I re-read the stored record.

  **Remedy:** any prescribed command whose argument carries prose or identifiers should be documented **single-quoted, or fed from a file or stdin**. The current documented form silently destroys exactly the technical content these commands exist to carry.
- **Evidence:** file:feedback/checkpoints/item-252-audit-binding-ledger-currency.jsonl; command:dotnet fsi .agents/skills/fs-gg-feedback-report/scripts/feedback-tool.fsx -- validate-checkpoint-state --cycle item-252-audit-binding-ledger-currency; issue:EHotwagner/S.I.R.#255

## §6 Doc-versus-behavior contradictions

The packed `independent-review` contract documents prose HTML-comment markers (`fsgg:independent-review:v1`, `fsgg:review-accepted:v1`) as the review evidence. `scripts/fsgg-coord landable` requires a typed `fsgg.coord.review-decision/v2` record produced by `fsgg-coord review record`, itself gated behind a durable entry from `fsgg-coord review wait`. This is the subject of EHotwagner/S.I.R.#255, held by a sibling lane this pass, to which I relayed the reproduction and the recovered wire shapes.

Narrower, same class: the packed skills' PR-body guidance permits a `Refs #<n>` form that disables `verify-paths` (§4.3).

A fourth, and the one that gates the board's own completion — **the validator rejects two of the five statuses it itself defines.** `FeedbackReportTool.fs:36` declares the critic vocabulary as `[ "actionable"; "incomplete"; "unsupported"; "duplicate"; "positive-pattern" ]`, and the same file then makes two of those values fatal: *"actionability: %s remains %s and cannot be handed off as actionable"* (`.agents` mirror line 803, `.claude` line 707) is added to the error list unconditionally for `incomplete` and `unsupported`; *"cannot be %s while missing facts are recorded"* (817 / 721) forbids `missingFacts` on an `actionable` finding; and *"cannot be %s with evidence result"* (889 / 793) forbids any non-`verified` locator on one. The only statuses that can validate are `actionable` with zero missing facts and every locator verified, `duplicate`, and `positive-pattern`.

SKILL.md 145-148 instructs the opposite, and at claim level rather than validity level: *"preserve the honest reduced disposition"*, and the skill and driver *"must not claim an actionable handoff."* The prose tells the author to keep the honest grade; the tool makes keeping it fatal.

The consequence is the reason this one matters most. An author holding an unprovable finding has three routes: inflate it, which validates and is false; delete it, which validates and loses it silently; or preserve it honestly, which does not validate and blocks the item's handoff. **Two of the three routes that work are dishonest, and the honest one fails closed** — and nothing in the resulting artifact shows which route was taken. That pressure is applied by the tool that certifies the honesty documentation.

This report took a fourth route, which is a correct disposition **and** a workaround: the two unprovable findings were structurally moved out of §4 into the accepted observations in §3. It should not be read as evidence that the contract is sound. Filed as EHotwagner/S.I.R.#269, blocked on #267 because the authoritative mirror must be settled before the file is repaired — the two copies carry identical logic about 96 lines apart, so a line-number citation is meaningless without naming the mirror.

A third, smaller one found while validating this report: the two skills that jointly define the feedback gate use **different phase vocabularies for the same concept**. `work-board`'s `feedback-contract.md` mandates the §1 envelope read `onboarding-first-build, lifecycle-authoring-or-not-used, implementation-test-evidence, verify-ship-pr`, and its validator compares that line against its own `--phases` argument. `fs-gg-feedback-report`'s `checkpoint --phase` takes `scaffold-onboarding`, `implementation-test-evidence`, `verify-ship-pr`. A third variant exists in `work-roadmap/references/feedback-contract.md:17`, which uses `lifecycle-authoring` without the `-or-not-used` suffix. Nothing reconciles the three, so a conforming report's envelope names two phases that cannot appear in any checkpoint, and a reader comparing the artifacts sees a mismatch that is actually compliance.
